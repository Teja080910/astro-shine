1Astrologer Review & Approval

Bug confirmed — UI gap, server already supports it

What works: the Review modal offers Approve and Reject, a rejection note is optional, rejected astrologers are counted and filterable, and a rejected badge plus note are shown.

What is broken: the Review button only renders when the status is pending:

{a.verificationStatus === 'pending' && (
  <button onClick={() => { setVerify(a); ... }}> Review </button>
)}

Once an astrologer is rejected, that button disappears and there is no other control to change the decision. The row still shows in the Rejected filter, but only View is available — so re-approving is impossible from the UI, exactly as reported.

Server is not the blocker. astrologers.service.ts:243 verify() simply writes the new status and notifies the astrologer — it has no "only from pending" guard. Calling it with approved on a rejected astrologer succeeds today. This is purely a missing button.

Fix

  • Show the Review/Manage button for pending, approved and rejected (label it Review when pending, Change otherwise).
  • Never hide the action — only the note field should be conditional.
  • Add an explicit Re-open review affordance so a rejection is visibly reversible.

2Wallet Management — dates & admin access

Bug confirmed — date filtering does not exist

The admin wallet page lists balances and totals, and supports a search + pagination. But a search for any date control returns nothing:

web/src/app/wallet/page.tsx (155 lines) — zero occurrences of date, Date or filter. There is no date column, no date range picker, and no date parameter sent to the API.

Admin wallet access itself does exist (getWalletByAdminId, and the page loads /wallet for the logged-in admin), so that half of the claim is already satisfied. What is missing is the ability to scope records by date.

Fix

  • Add a from/to date range picker to the wallet table (same component the wallet filters already use).
  • Send from/to to /wallet/all and filter on transactions.createdAt; show a Created column.
  • Validate from <= to and cap the range (e.g. 12 months) to keep the query cheap.

Note on "live key and admin account configuration": that is a credentials/ops task, not a code bug. Razorpay keys live in server/.env (RAZORPAY_KEY_ID/SECRET) — switching test→live is a config change, and the admin Settings page currently has no Razorpay section at all.

3Gifts — commission & "Redeemed"

Critical bug confirmed — 100% of the gift goes to the astrologer

This is the most serious finding. Calls and chat both split revenue through a commission service. Gifts do not.

server/src/modules/gifts/gifts.service.ts — grep -c commission returns 0. The send path credits the receiver the full amount and records fee: '0', netAmount: amountStr: 
balance: sql`${schema.wallets.balance} + ${amountStr}::decimal`,   // full amount
fee: '0',
netAmount: amountStr,
Compare calls.service.ts:195, which correctly calls commissionService.distributeEarnings(...).

So on every gift the platform earns nothing, and the astrologer receives the entire sum — directly contradicting the requirement that commission be deducted and only the remainder credited.

"Redeemed" is cosmetic

redeemGift() only flips a flag:

.set({ isRedeemed: true, redeemedAt: new Date() })

No wallet balance, no transaction row, no payout changes. But the gift is already credited at send time, so "Redeemed" has no financial meaning — it is a status with no consequence, which is exactly the confusion described.

Currently latent: this database has 0 gift transactions, so no money has been lost yet. Fixing it before gifts go live prevents a retroactive reconciliation problem.

Fix

  • Route gifts through commissionService.distributeEarnings like calls/chat: debit sender, credit astrologer amount × (1 − commission%), record platform share.
  • Store the split on the transaction (fee, netAmount) so reporting is truthful.
  • Decide the semantics of Redeemed. Two sane models:
    • Credit-on-send (current): drop "Redeemed" or relabel it "Acknowledged" — it is not money.
    • Credit-on-redeem: hold the gift, credit the astrologer only when redeemed, and make Redeemed the payout trigger. This matches the word's everyday meaning.
  • Whichever is chosen, show it in the astrologer's earnings breakdown so the number is explainable.

4Withdrawal Management

No bug found — already implemented

This claim does not hold up. The admin withdrawal page supports the full flow:

  • Lists requests with requester, amount, payout method and status.
  • Approve and Reject actions on pending requests, with a confirm dialog.
  • Status badges for pending, approved, completed, rejected.
  • Payout state surfaced separately (processed/completed).
The server side is real, not cosmetic: withdrawal.service.ts:367 approve() runs in a transaction, takes FOR UPDATE row locks on both the request and the astrologer's wallet, refuses non-pending requests, and debits the balance.

If admin still cannot process withdrawals in practice, the likely cause is credentials or the payout provider, not this code. Worth reproducing before scheduling work.

5Call Log Search

Bug confirmed — two independent defects

Defect A — the search only runs on Enter

SearchInput calls onEnter from the keydown handler alone. Typing a query and clicking elsewhere does nothing; the term is only committed when Enter is pressed. Clear (×) also only works because it explicitly calls onEnter('').

Defect B — the SQL joins conditions with AND instead of OR

calls.service.ts:20-45 pushes type, status, userId and astrologerId as separate conditions and combines them with and(...). A single search term must therefore match every column at once — practically impossible.

Reproduced against the live database (5 call logs, 2 of type video):

QueryRows returnedExpected
type ILIKE '%video%' AND status ILIKE '%video%' (current)02
type ILIKE '%video%' OR status ILIKE '%video%'22

Fix

  • Combine the searchable columns with or(...), not and(...). The identical and(...) mistake is in searchWhere() and in findAll().
  • Debounce the input (~300 ms) and search as the user types; keep Enter as an immediate trigger.
  • Audit the other nine pages using the same onEnter-only pattern (orders, reports, support, withdrawals, gifts, blogs, videos, muhurat) — they share Defect A.

6Pooja Image Icon

Bug confirmed — the field exists in the DB but not in the form

The database stores an image for each pooja, but the admin form never touches it:

server/src/db/schemas/mandir-pooja.ts:7 declares image: text('image').
web/src/app/mandir-pooja/page.tsx reads only name, description and price, and saves { name, description, price } — no image anywhere, and no icon column in the table.

Consequence: any image previously seeded shows, but a new pooja can never get one, and admins cannot fix a wrong image — which is what "needs to be checked and corrected" describes.

Fix

  • Add an image URL/upload field to the pooja form, included in the save payload.
  • Show a thumbnail column in the list so a broken image is visible immediately.
  • Validate the URL/extension and fall back to a placeholder icon when missing.
  • Confirm the mobile app consumes the same field so admin changes appear there.

7Reports & Review Management

Partly confirmed — actions exist but the status model is wrong

Already present: View, Edit and Delete per row, a details modal, and a resolve endpoint that notifies both parties.

What is wrong:

  • Only two statuses exist — pending and reviewed. The requested Open / Resolve vocabulary is absent.
  • Resolve disappears once reviewed (r.status !== 'reviewed' && ...), so a wrongly-resolved report can never be re-opened from the UI — the same shape of bug as #1.
  • Resolved is not an action, only a badge. There is no explicit Resolved control in the action column, which is why the options look incomplete.
web/src/app/reports/page.tsx:13 const STATUSES = ['pending', 'reviewed'] as const; — the Edit dropdown can only ever offer those two.

Fix

  • Model three states: open → resolved, with re-open supported. Either migrate pending/reviewed or map them for display.
  • Always render the full action set — View, Edit, Open/Resolve (toggling), Resolved (state chip), Delete — instead of hiding Resolve.
  • Expose both options in the Edit dropdown, as requested.
  • Re-opening should clear resolvedAt/resolvedBy; the service already does this.
